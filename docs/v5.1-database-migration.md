# V5.1 Database Foundation Migration Documentation

**Migration Version**: `4`  
**Target Branch**: `feature/library-source-foundation`  
**Base Architecture**: `docs/v5-architecture.md`

## 1. Overview & Objective

V5.1 establishes the core SQLite relational database foundation required for future discovery features (Movies, Artists/Singers/Composers/Actors, Charts/Top 100, User Ratings, Favorites, and Playlists) without modifying, rewriting, or breaking the validated download and canonical library engine.

All 11 new tables and their associated indices were added through **Migration 4**, preserving 100% backward compatibility with existing tables (`songs`, `song_sources`, `downloads`, `discovery_context`, `library_locations`).

---

## 2. Important Architectural & Schema Decisions

### A. Normalized Song-Movie Relationship (`song_movies`) vs `songs.movie_id`
* **Original Suggestion**: In preliminary architecture discussions, adding `songs.movie_id` was considered.
* **Decision & Rationale**: We deliberately **did not add `movie_id` to the `songs` table**.
  1. A canonical song track can appear in original soundtrack releases, re-releases, compilation albums, and multiple discovery provider sources.
  2. Forcing a single `movie_id` column onto `songs` would corrupt canonical deduplication and violate 3NF.
  3. Instead, a many-to-many relationship table `song_movies (song_id, movie_id, track_number)` was implemented. This allows songs to link to multiple movies or compilations without mutating `songs`.

### B. Normalized Song-Artist Relationship (`song_artists`) vs `songs.artist`
* **Decision**: We preserved the existing `songs.artist` string field intact for backward compatibility with existing downloads, filesystem reconciliation, and planners.
* **Enhancement**: We introduced `song_artists (song_id, artist_id, role)` to support rich multi-artist relationships (e.g. multiple singers, music directors, lyricists) for future V5 search and filtering.

### C. Foreign Key & Cascade Deletion Semantics
* SQLite disables foreign key enforcement by default unless explicitly configured per-connection. To maintain backward compatibility with legacy tests that use simulated/detached keys while ensuring clean data management:
  - **DDL Level**: All relational tables declare standard `FOREIGN KEY ... ON DELETE CASCADE`.
  - **DAO Layer**: Methods `delete_movie`, `delete_artist`, `delete_playlist`, and `delete_chart` explicitly delete their associated junction/child records (`movie_actors`, `movie_composers`, `song_movies`, `song_artists`, `playlist_items`, `chart_entries`) inside a transaction before removing the parent entity.
  - **Song Deletion Safety**: Deleting a movie, artist, playlist, or chart **never** deletes canonical songs or actual physical audio files.

## 3. Implemented Tables & Schemas

### 1. `movies`
Represents films, albums, or soundtracks.
```sql
CREATE TABLE IF NOT EXISTS movies (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    title_normalized TEXT NOT NULL,
    year INTEGER,
    director TEXT,
    poster_url TEXT,
    banner_url TEXT,
    local_poster_path TEXT,
    track_count INTEGER DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_movies_title_normalized ON movies(title_normalized);
CREATE INDEX IF NOT EXISTS idx_movies_year ON movies(year);
```

### 2. `artists`
Extensible entity for singers, music directors, lyricists, actors, and composers.
```sql
CREATE TABLE IF NOT EXISTS artists (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    name_normalized TEXT NOT NULL,
    role TEXT,
    photo_url TEXT,
    local_photo_path TEXT,
    bio TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_artists_name_normalized ON artists(name_normalized);
CREATE INDEX IF NOT EXISTS idx_artists_role ON artists(role);
```

### 3. `movie_actors`
Junction table linking actors to movies with optional character names.
```sql
CREATE TABLE IF NOT EXISTS movie_actors (
    movie_id INTEGER NOT NULL,
    actor_id INTEGER NOT NULL,
    character_name TEXT,
    PRIMARY KEY (movie_id, actor_id),
    FOREIGN KEY (movie_id) REFERENCES movies(id) ON DELETE CASCADE,
    FOREIGN KEY (actor_id) REFERENCES artists(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_movie_actors_actor ON movie_actors(actor_id);
```

### 4. `movie_composers`
Junction table linking music directors / composers to movies.
```sql
CREATE TABLE IF NOT EXISTS movie_composers (
    movie_id INTEGER NOT NULL,
    composer_id INTEGER NOT NULL,
    PRIMARY KEY (movie_id, composer_id),
    FOREIGN KEY (movie_id) REFERENCES movies(id) ON DELETE CASCADE,
    FOREIGN KEY (composer_id) REFERENCES artists(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_movie_composers_composer ON movie_composers(composer_id);
```

### 5. `song_artists`
Normalized link between canonical songs and artists with role attribution (`singer`, `composer`, `lyricist`, `featuring`).
```sql
CREATE TABLE IF NOT EXISTS song_artists (
    song_id INTEGER NOT NULL,
    artist_id INTEGER NOT NULL,
    role TEXT NOT NULL DEFAULT 'singer',
    PRIMARY KEY (song_id, artist_id, role),
    FOREIGN KEY (song_id) REFERENCES songs(id) ON DELETE CASCADE,
    FOREIGN KEY (artist_id) REFERENCES artists(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_song_artists_artist ON song_artists(artist_id, role);
CREATE INDEX IF NOT EXISTS idx_song_artists_song ON song_artists(song_id);
```

### 6. `song_movies`
Normalized link between canonical songs and movies/albums with track sequencing.
```sql
CREATE TABLE IF NOT EXISTS song_movies (
    song_id INTEGER NOT NULL,
    movie_id INTEGER NOT NULL,
    track_number INTEGER,
    PRIMARY KEY (song_id, movie_id),
    FOREIGN KEY (song_id) REFERENCES songs(id) ON DELETE CASCADE,
    FOREIGN KEY (movie_id) REFERENCES movies(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_song_movies_movie ON song_movies(movie_id);
CREATE INDEX IF NOT EXISTS idx_song_movies_song ON song_movies(song_id);
```

### 7. `user_song_metadata`
Stores user-specific data (ratings 1–5, favorites, tags, notes) without provider overwrites.
```sql
CREATE TABLE IF NOT EXISTS user_song_metadata (
    song_id INTEGER PRIMARY KEY,
    rating INTEGER CHECK (rating IS NULL OR (rating >= 1 AND rating <= 5)),
    is_favorite INTEGER NOT NULL DEFAULT 0,
    notes TEXT,
    tags TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    favorited_at TEXT,
    last_rated_at TEXT,
    FOREIGN KEY (song_id) REFERENCES songs(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_user_song_metadata_rating ON user_song_metadata(rating);
CREATE INDEX IF NOT EXISTS idx_user_song_metadata_favorite ON user_song_metadata(is_favorite);
```

### 8. `playlists`
User and smart playlist definitions.
```sql
CREATE TABLE IF NOT EXISTS playlists (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    description TEXT,
    cover_url TEXT,
    is_smart INTEGER NOT NULL DEFAULT 0,
    smart_criteria_json TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

### 9. `playlist_items`
Ordered entries within a playlist with composite uniqueness.
```sql
CREATE TABLE IF NOT EXISTS playlist_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    playlist_id INTEGER NOT NULL,
    song_id INTEGER NOT NULL,
    position INTEGER NOT NULL,
    added_at TEXT NOT NULL,
    UNIQUE(playlist_id, song_id),
    FOREIGN KEY (playlist_id) REFERENCES playlists(id) ON DELETE CASCADE,
    FOREIGN KEY (song_id) REFERENCES songs(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_playlist_items_playlist ON playlist_items(playlist_id, position);
CREATE INDEX IF NOT EXISTS idx_playlist_items_song ON playlist_items(song_id);
```

### 10. `charts`
Curated snapshots (e.g., Top 100, Trending Weekly, Retro Hits).
```sql
CREATE TABLE IF NOT EXISTS charts (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    chart_type TEXT NOT NULL,
    provider_name TEXT,
    snapshot_date TEXT NOT NULL,
    created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_charts_chart_type ON charts(chart_type);
CREATE INDEX IF NOT EXISTS idx_charts_snapshot_date ON charts(snapshot_date);
```

### 11. `chart_entries`
Ranked track listings for a given chart snapshot.
```sql
CREATE TABLE IF NOT EXISTS chart_entries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    chart_id TEXT NOT NULL,
    rank INTEGER NOT NULL,
    previous_rank INTEGER,
    song_id INTEGER,
    raw_title TEXT NOT NULL,
    raw_artist TEXT,
    raw_movie TEXT,
    UNIQUE(chart_id, rank),
    FOREIGN KEY (chart_id) REFERENCES charts(id) ON DELETE CASCADE,
    FOREIGN KEY (song_id) REFERENCES songs(id) ON DELETE SET NULL
);
CREATE INDEX IF NOT EXISTS idx_chart_entries_chart_rank ON chart_entries(chart_id, rank);
CREATE INDEX IF NOT EXISTS idx_chart_entries_song ON chart_entries(song_id);
```

## 4. Migration Execution & Safety

1. **Idempotency**: All `CREATE TABLE` and `CREATE INDEX` statements use `IF NOT EXISTS`. The migrator verifies `schema_version` before execution.
2. **Deterministic Versioning**: The project's schema version has been bumped from `3` to `4`.
3. **Data Preservation**: Tested against:
   - Fresh (empty) databases.
   - Populated databases with existing songs, sources, and downloads.
   - Multiple sequential executions of `migrator.migrate()` without errors or data duplication.
